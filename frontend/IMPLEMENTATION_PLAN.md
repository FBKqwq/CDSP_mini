# TCM LLM Chart 微信小程序实施计划

## 1. 交付判断

需求方向正确，但当前不能把“完整上线”当作单纯前端编码任务。现有目录只有需求文档，且真实 AppID、HTTPS/WSS 网关、Token 契约、字段字典、WebSocket 事件样例、测试账号和 UI 评审结论尚未提供。

本轮先交付一个独立、可构建、可测试、可运行 Mock 业务闭环，并把真实服务封装在统一 API 和 Socket 边界后。这样既能完成 UI 与核心会话机制评审，也不会把旧服务地址和不稳定字段扩散到页面。

## 2. 目标—差距—方向

| 项目 | 结论 |
|---|---|
| 最终目标 | 医务用户在微信小程序完成登录、患者选择、AI 问诊、诊断、报告和处方闭环，并在切换上下文和弱网恢复时不串数据。 |
| 当前差距 | 当前目录无工程；桌面实现依赖 Element Plus、DOM、iframe、浏览器 WebSocket 和模块级共享状态。 |
| 根因 | 业务协议、桌面展示和浏览器运行时耦合，且患者会话没有独立生命周期边界。 |
| 技术方向 | 独立 uni-app 工程；版本化网关 API；Pinia 明确状态所有权；实例级 Socket；`sessionVersion` 过滤旧异步回调；Canvas 与安全 Markdown 节点渲染。 |
| 当前完整切片 | 可在 H5 和微信开发者工具运行的移动端完整演示；真实联调只需替换环境变量和完成 DTO 契约，不改页面。 |

## 3. 分阶段计划

### 阶段 0：基线与评审（当前交付）

- 建立需求追踪、领域对象、错误码和 REST/WSS 边界。
- 提供登录、问诊默认/流式、诊疗、报告/处方、选择面板和异常状态的可交互高保真实现。
- 明确 Mock 与真实网关切换方式。

退出条件：`npm run check` 通过；390×844、320×568 和 430×932 无页面级横向溢出；核心状态可演示。

### 阶段 1：黄金链路联调

- 冻结登录、患者、疾病、专家、AI 实例和流事件 DTO。
- 配置开发 HTTPS/WSS 合法域名与 AppID。
- 跑通登录—患者—实例—WSS—首段输出。

退出条件：开发者工具和至少一台真机完成真实接口首轮问诊。

### 阶段 2：完整问诊

- 接入患者增删查选、记录保存恢复、进入诊断。
- 验证断网重连、前后台恢复、Token 过期和快速上下文切换。

退出条件：旧 Socket 事件无法污染新患者；服务端记录可校正本地状态。

### 阶段 3：诊疗与报告

- 冻结诊断、雷达图、报告、对比和处方字段。
- 完成真实数据映射、空字段和长文本专项测试。

退出条件：诊断与报告验收项通过，客户端不推导医疗结论。

### 阶段 4：质量与发布

- iOS/Android 真机、弱网、前后台、包体和隐私专项测试。
- 配置监控、体验版、发布和回滚说明。

退出条件：需求文档 Definition of Done 全部具备可审计证据。

## 4. 真实联调前置清单

1. 微信小程序 AppID、主体与体验成员。
2. 开发/测试/生产 HTTPS 和 WSS 合法域名及证书。
3. `/api/v1` REST 响应样例、错误码和字段字典。
4. WSS 鉴权方式、事件 ID、轮次、顺序、重放和完成语义。
5. 脱敏测试账号与患者。
6. 网关负责人、部署环境和发布回滚负责人。

这些缺失项会阻塞真实接口和真机验收，但不阻塞当前工程、UI 和核心会话机制开发。
